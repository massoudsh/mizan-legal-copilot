# معماری فنی — میزان (Mizan)

## ۱. نمای کلی اجزای سیستم

```
                         ┌─────────────────────────┐
                         │   پایگاه دانش قانونی      │
                         │  قوانین · آیین‌نامه‌ها ·   │
                         │  رویه‌های اجرایی · ابلاغیه‌ها│
                         └────────────┬────────────┘
                                      │ (RAG / retrieval)
┌──────────────┐    ┌────────────┐   ▼   ┌────────────────┐   ┌──────────────────┐
│  Ingestion    │───▶│  Document   │──────▶│  Risk Engine    │──▶│ Decision & Action │
│ (آپلود سند/   │    │  Parser     │       │ (LLM + Rules +  │   │      Layer        │
│  قرارداد)     │    │(PDF/DOCX/OCR)│      │  Org Context)   │   │ (مسیر اقدام،      │
└──────────────┘    └────────────┘       └───────┬────────┘   │  Decision Log،    │
                                                   │            │  Escalation)      │
                          ┌────────────────────────┘            └────────┬─────────┘
                          ▼                                              ▼
                 ┌─────────────────┐                          ┌──────────────────┐
                 │  Org Profile     │                          │  Dashboard / API  │
                 │ (مدل درآمدی،     │                          │  (خروجی مدیریتی)  │
                 │  وضعیت پرسنل)    │                          └──────────────────┘
                 └─────────────────┘
```

## ۲. اجزا

### ۲.۱ لایه دریافت (Ingestion)
دریافت سند/قرارداد/تصمیم از طریق آپلود مستقیم یا (در فازهای بعد) اتصال به سیستم‌های داخلی سازمان (ایمیل، DMS، ERP).

### ۲.۲ Document Parser
استخراج متن از PDF/DOCX/تصویر (OCR برای اسناد اسکن‌شده). خروجی: متن ساخت‌یافته + متادیتا (نوع سند، تاریخ، طرفین).

### ۲.۳ پایگاه دانش قانونی (Legal Knowledge Base)
مجموعه‌ای از قوانین، آیین‌نامه‌ها، بخشنامه‌ها، ابلاغیه‌ها و **رویه‌های اجرایی مستندشده** (تفاوت متن خام قانون با
برداشت عملیاتی رگولاتور). در فاز v2 با معماری RAG (embedding + vector search) ایندکس می‌شود تا موتور ریسک بتواند
هنگام تحلیل، مرتبط‌ترین مواد/رویه‌ها را بازیابی کند. حساسیت به **تاریخ ابلاغ/اجرا** یک فیلد کلیدی متادیتاست تا
تحلیل همیشه بر اساس آخرین نسخه‌ی معتبر باشد.

### ۲.۴ Org Profile (پروفایل ریسک سازمان)
مدل درآمدی، تعداد و نوع قراردادهای پرسنل، صنعت، سابقه‌ی تصمیم‌های ثبت‌شده. این پروفایل به موتور ریسک context
می‌دهد تا تحلیل عمومی نباشد بلکه مختص وضعیت همان سازمان باشد.

### ۲.۵ Risk Engine
هستهٔ تحلیلی، ترکیبی از:
- **قواعد قطعی (Rule-based)** برای مواردی با آستانه‌ی روشن قانونی (مثلاً سقف تعداد قرارداد موقت، نصاب‌های مالیاتی)
- **تحلیل LLM** برای تفسیر متن قرارداد/سند در بستر رویه‌های اجرایی و پروفایل سازمان
- خروجی ساخت‌یافته: `دسته‌بندی ریسک`، `سطح ریسک`، `توضیح مدیریتی`، `مسیر اقدام پیشنهادی`، `نیاز به مشاور انسانی؟`

جزئیات پیاده‌سازی MVP در `backend/app/risk_engine.py`.

### ۲.۶ Decision & Action Layer
- **Action Path**: تبدیل هر یافته‌ی پرریسک به گام‌های اجرایی مشخص
- **Decision Log**: ثبت تصمیم‌های حساس به همراه مستندات پشتیبان برای دفاع‌پذیری در آینده (audit trail)
- **Escalation**: وقتی سطح ریسک از آستانه‌ی اطمینان مدل عبور کند یا پیچیدگی حقوقی بالا باشد، مورد برای بررسی
  مشاور انسانی پرچم‌گذاری می‌شود — میزان جایگزین مشاور حقوقی نیست.

### ۲.۷ Dashboard / API
خروجی نهایی به زبان مدیریتی برای CEO/CFO/HR/Legal، با نمای تجمیعی روند ریسک در طول زمان (v2).

## ۳. جریان داده (Data Flow) — سناریوی MVP

```
کاربر سند را آپلود می‌کند
   → Document Parser متن را استخراج می‌کند
   → Risk Engine متن + پروفایل سازمان را به LLM/قواعد می‌دهد
   → خروجی ساخت‌یافته (JSON: findings, risk levels, actions) برگردانده می‌شود
   → API نتیجه را به شکل قابل‌فهم مدیریتی نمایش می‌دهد
```

## ۴. Stack پیشنهادی

| لایه | فناوری | دلیل انتخاب |
|---|---|---|
| Backend API | FastAPI (Python) | سبک، async، مناسب سرویس‌های LLM-heavy |
| پایگاه داده | PostgreSQL (+ pgvector در v2) | قابل اتکا، پشتیبانی بومی از JSON و بردار |
| ذخیره‌سازی سند | S3-compatible object storage | مقیاس‌پذیر، جدا از دیتابیس |
| LLM | قابل تعویض از طریق env (OpenAI-compatible endpoint) | عدم قفل‌شدگی به یک ارائه‌دهنده |
| Frontend (فازهای بعد) | Next.js | برای داشبورد مدیریتی تعاملی |

## ۵. امنیت و محرمانگی

اسناد سازمانی (قرارداد، اطلاعات پرسنل، مدل درآمدی) بسیار حساس‌اند:
- رمزنگاری داده در حالت سکون (at-rest) و انتقال (in-transit)
- کنترل دسترسی مبتنی بر نقش (RBAC) بین سازمان‌ها و کاربران
- لاگ حسابرسی (audit log) برای هر دسترسی به اسناد و تحلیل‌ها
- عدم نگهداری کلید/سکرت در کد یا مخزن گیت (استفاده از `.env` و secret manager)
- جداسازی داده هر سازمان (tenant isolation) در معماری چندمستأجری

## ۶. نقشه‌ی پیاده‌سازی فعلی (این ریپو)

`backend/` شامل MVP سرویس تحلیل ریسک است:
- `app/document_parser.py` — استخراج متن از PDF/DOCX/TXT
- `app/llm_client.py` — کلاینت LLM قابل‌تعویض با fallback قاعده‌محور وقتی کلید API تنظیم نشده
- `app/risk_engine.py` — پرامپت‌سازی، فراخوانی LLM، اعتبارسنجی خروجی ساخت‌یافته
- `app/schemas.py` — مدل‌های Pydantic برای ورودی/خروجی
- `app/main.py` — FastAPI با endpoint آپلود و تحلیل سند

این پیاده‌سازی نقطه‌ی شروع فاز MVP بخش «آپلود قرارداد → تحلیل ریسک» است؛ پایگاه دانش قانونی، Decision Log و
Dashboard در فازهای بعدی طبق نقشه‌راه PRD اضافه می‌شوند.
